# 匿名对局数据系统（R757）

> 目的：把「哪张卡没人要 / 哪个精英在屠杀 / 玩家在哪一层不玩了」变成**可量化**的东西。
> 只在**发布版**生效，测试版不写、不弹、设置页也不出现。

## 一、为什么不是「加几个计数器」

`ProfileData.stats` 里的 `card_play:<id>` 只回答「这张卡一共被打出几次」，
回答不了三个关键问题：

1. **它被提议过几次**（选择率的分母）—— 没有分母，「被选 30 次」到底是热门还是便宜？
2. **选了它以后那局赢没赢**（选择的收益）—— 计数器是跨局累计的，追不到单局结果；
3. **选了却从没用过**（死卡）—— 高分卡占着卡位却没人打，比没人选更该改。

所以要一条**只追加的事件流**：谁在什么处境下，从哪几个候选里选了谁，那一局后来怎么了。

## 二、三层结构

| 层 | 文件 | 说明 |
|---|---|---|
| 采集 | `scripts/telemetry.gd` | `user://telemetry.jsonl`，一行一条 JSON，只追加 |
| 上报 | `scripts/telemetry_uploader.gd` | 玩家同意后把**新增部分**批量 POST；偏移记在 `user://telemetry.sent` |
| 询问 | `scripts/telemetry_consent.gd` | 发布版首次进标题页弹一次；`telemetry_opt_in` 0=未问 / 1=同意 / 2=拒绝 |
| 分析 | `tools/analyze_balance.py` | 选择率 / 分层 lift / 掉血 / 死亡点 / 删卡负票 / 商店成交 |
| 后端 | `tools/telemetry_server/` | 本地接收器 + Cloudflare Worker 示例 |

**采集与上报是两件事**：本机记录不需要同意（数据没出机器），弹窗只管「要不要往外发」。
默认 `0` = 不发。设置页「显示」页多一项「匿名对局数据」，可随时反悔。

## 三、事件字典

| `ev` | 关键字段 |
|---|---|
| `run_start` | `seed` `cls` `diff` `runs` `max_diff` `deepest` `wins` `sim` |
| `offer` | `oid` `k`(card/relic/tool) `src` `cand[]` `layer` `hp` `mhp` `gold` `deck` |
| `pick` | `oid` `k` `id` `cand[]` `ms` `skip` |
| `battle` | `key` `name` `tier` `layer` `win` `out` `turns` `hp0` `hp1` `dmg_in` `units[]` `secs` |
| `deck` | `op`(del/transform) `old` `new` |
| `shop_shelf` | `items[]`(k/id/price) `layer` `gold` `hp` `deck` |
| `shop` | `k` `id` `cost` `bought` |
| `run_end` | `win` `out` `secs` `layer` `battles` `bwins` `deaths` `played[]` `relics[]` |

`out`：`win` / `lose` / `flee` / `interrupted`。
`interrupted` 由 `RunRecord.finish("interrupted")` 交（关窗口 / 崩溃 / 开新局顶掉上一局）。

## 四、几个关键口径（都是踩过坑才定下来的）

1. **选择率的分母 = 被提议次数。** 跳过整组也要留在分母里 —— 「摆出来没人要」比「没人选」
   更能说明问题。商店另记 `shop_shelf` 快照，没上过货架的卡不参与商店成交率。
2. **胜率要分层。** 同一张卡在难度 0 和 11 的差异，比强弱卡的差异还大。分析脚本按难度分组
   算 `lift = 带这张卡的通关率 − 同难度基线通关率`，并输出 Wilson 置信区间；样本不足的
   一律显示 `?`，不假装有结论。
3. **「选了却没用」列 = 死卡。** 由 `card_play:*` 的局内差集算出（`run_end.played`），
   不需要在出牌热路径埋点。
4. **敌人看掉血，不只看胜率。** 普通战胜率常年 95%+；`dmg_in / 最大生命` 才是敏感指标。
5. **玩家熟练度必须打标。** `run_start.runs`（开局前总局数）/ `max_diff` / `deepest` ——
   强玩家爱选上限卡、弱玩家爱选保命卡，不分层会把回血卡算成神卡。
6. **`run_end` 要当场交。** 挂在 `mark_run_won()` / `mark_run_lost()` 上，不等结算页点「确定」
   —— 玩家直接关窗口是很常见的操作，那样这一局会从统计里整条消失。

## 五、怎么用

```bash
# 编辑器里模拟发布版采集
godot --path . -- --release --telemetry

# 出报告（默认去 Godot user:// 找）
python tools/analyze_balance.py --csv out/
```

机器人先验（卡池 320 张时唯一有统计功效的来源）：

```bash
python tools/ai_play/launch.py --headless --sim --telemetry
python tools/ai_play/balance_sim.py --runs 20
python tools/analyze_balance.py --sim
```

AI 觉得强、玩家不用 → 太贵 / 太慢 / 需要配合；AI 不选、玩家抢 → 体感爽但数值弱。
这两类差异是调数值收益最高的地方。

## 六、实测踩到的坑

- **`FileAccess.WRITE_READ` + `seek_end()` 不是追加。** 打开后从头覆盖，表现是
  「每次启动把整份事件流重写一遍」，上一整局的数据成批消失。必须用 `READ_WRITE`
  （文件须已存在，先建空文件）。`test_engine` 有一条源码锁守着这件事。
- **`launch.py` 端口复用会连到老进程。** 调试时最容易被骗：看到「已在运行」就连上了一个
  跑着旧代码的进程，报出早已修好的错误。改代码后先 `launch.py --stop`，必要时
  `taskkill /IM Godot_v4.3-stable_win64.exe /F`。
- **`--sim` 与真实数据必须分开算。** bot 的选卡偏好是固定策略，混进玩家数据会把
  「AI 认为强」当成「玩家喜欢」。

## 七、隐私

- 不采设备 id、账号、IP；`run` 只是「种子 + 毫秒时间戳」，跨局不可关联。
- 服务端示例也明确**不要**记 IP / UA / Referer。
- 默认不上传；同意后才发；设置页可随时关。
- 本机事件流是玩家自己的文件，上传成功后也**不删**（留着方便复查）。
